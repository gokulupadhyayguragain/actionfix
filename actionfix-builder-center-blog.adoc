== Article description / teaser
A failing GitHub Actions run can feel like a wall of red text. I am building ActionFix to turn that confusion into one understandable next step, with evidence from the logs, a copyable suggestion, and a calm explanation powered by AWS.

== What my agent does — and who it helps

GitHub Actions is one of the easiest ways to start automating software checks and deployments. But when a workflow fails, a beginner may see dozens of lines of output and have no idea where to start. Error messages often assume familiarity with Node.js, package management, permissions, YAML, or GitHub runners. For students learning CI/CD, the actual problem can be smaller than the message makes it look.

That is the situation that inspired *ActionFix*, an agent designed to help students and early-career developers understand a failed GitHub Actions workflow. The goal is not to rewrite someone's entire pipeline or automatically push changes to their repository. The goal is simpler: show what likely failed, point to the exact evidence, and suggest one sensible first check.

The user pastes the failure log and can optionally include the workflow YAML. ActionFix analyzes the input and returns a short response organized around five questions: What happened? Which line supports that conclusion? What should I try first? How do I verify the change? What should I share if the diagnosis is still uncertain?

== How I built it

I designed ActionFix as a small web app backed by AWS, with a deliberate split between deterministic checks and natural-language guidance. The browser is responsible for a friendly input form and readable result cards. An AWS Lambda function handles validation, diagnostic tool selection, and the API response. Amazon Bedrock supplies the language model used to turn a technical diagnosis into a clear explanation.

The diagnostic tools check recognizable failure signatures. For example, `Cannot find module 'pdfkit'` suggests a missing Node.js dependency; a file-not-found error may require checking whether the workflow checked out the repository or used the correct working directory; and an `AccessDenied` message calls for careful examination of the relevant action and permission settings. These checks are evidence, not proof of a complete root cause. The agent must avoid claiming it inspected a repository it never accessed.

The key architectural choice is to keep the diagnosis bounded. A model may be good at explaining an error, but it should not invent details about a workflow. The backend extracts evidence, chooses and runs tools such as `classify_error` and `inspect_workflow`, then asks Bedrock to express the result in plain language. If an error message is too vague, the agent asks for the missing information rather than filling gaps with guesses.

== The experience — the one detail I wanted users to enjoy

The feature I care about most is called *One Fix First*. Instead of showing an intimidating wall of generated text, ActionFix presents a short sequence: *Problem -> First fix -> Verify*. The evidence from the log is visible alongside the suggestion, and an optional "Why does this work?" control lets curious users go deeper without overwhelming people who just want their pipeline running again.

I also want the first interaction to work even when someone has no error log ready. Sample failure buttons provide a safe way to explore the interface. A person can select a missing dependency example and immediately see the format of the answer. A copy action minimizes the friction of trying a recommended command or YAML adjustment in their own project.

Just as important is what the agent does when it is not sure. A line such as `Process completed with exit code 1` does not contain enough information for a trustworthy fix. ActionFix is designed to respond with a request for the preceding error lines and the relevant step. To me, an honest request for context is a better experience than a confident but invented answer.

== What I learned and what comes next

The most interesting lesson from this project is that a useful agent should be judged by how understandable its next action feels, not merely by how many words it generates. A narrow task, structured tools, good boundaries, and visible evidence can make a small application more trustworthy. Building for beginners also means writing error messages for humans instead of repeating technical jargon.

The MVP is intentionally read-only. A future version might integrate GitHub OAuth with carefully scoped permissions to fetch workflow logs on a user's request, generate draft pull requests for review, and keep a searchable knowledge base of common failures. Those are *future ideas*, not features claimed in this weekend submission.

For this challenge, I focused on a small, inspectable experience: paste the failure, understand the reason, and take one safer first step. If it helps even one newcomer move from "I have no idea what this log means" to "I know what to check next," that is the outcome I wanted.
